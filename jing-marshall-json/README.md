# jing-marshall-json

A high-performance JSON serialization/deserialization format implementation built on jing-marshall metadata.

## Overview

jing-marshall-json is the default JSON format implementation for the jing-marshall framework. It consumes the metadata generated by `jing-marshall-processor` (via `MarshallFacade`) to serialize and deserialize objects to/from JSON, without any runtime reflection.

Key characteristics:

- **No reflection** — all field access goes through generated `VarHandle` calls (classes) or record accessors (records).
- **SIMD-accelerated** — string serialization/deserialization and UTF-8 validation use the Java Vector API for batch processing.
- **Dual buffer support** — every operation works with both on-heap (`byte[]`) and off-heap (`MemorySegment`) buffers.
- **Avoids recursion** — uses an explicit node stack for nested structures, with configurable maximum nesting depth.
- **Custom type support** — register `MarshallTransformerFacade` implementations to convert custom types to/from JSON primitives.

Note: jing-marshall-json operates on `ReadBuffer` and `WriteBuffer`, meaning the entire JSON document must be loaded into memory. It is not suitable for streaming or parsing very large JSON files (e.g., multi-GB). For such cases, a streaming JSON parser would be more appropriate.

## Quick Start

### Serialize a Marshallable Object

```java
@Marshallable
public class User {
    private int id;
    private String name;
    private long score;

    // getters and setters ...
}
```

```java
JsonSerializer serializer = new JsonSerializer(JsonSerializerOption.defaultOption());
HeapWriteBuffer wb = new HeapWriteBuffer(1024);

User user = new User();
user.setId(42);
user.setName("alice");
user.setScore(100L);

serializer.serializeMarshallableObject(user, wb);
String json = new String(wb.toByteArray(), StandardCharsets.UTF_8);
// -> {"id":42,"name":"alice","score":100}
```

### Deserialize a Marshallable Object

```java
JsonDeserializer deserializer = new JsonDeserializer(JsonDeserializerOption.defaultOption());
String json = "{\"id\":42,\"name\":\"alice\",\"score\":100}";
HeapReadBuffer rb = new HeapReadBuffer(json.getBytes(StandardCharsets.UTF_8));

User user = deserializer.deserializeMarshallableObject(User.class, rb);
// user.id() == 42, user.name() == "alice", user.score() == 100
```

### Serialize with Indentation

```java
JsonSerializerOption option = JsonSerializerOption.builder()
    .indentationLevel(JsonIndentationLevel.TWO)
    .build();
JsonSerializer serializer = new JsonSerializer(option);
```

Output:
```json
{
  "id": 42,
  "name": "alice",
  "score": 100
}
```

### Serialize Collections and Maps

```java
// collections
List<User> users = List.of(user1, user2);
HeapWriteBuffer wb = new HeapWriteBuffer(1024);
serializer.serializeCollection(users, User.class, wb);

// maps (keys must be String or CharSequence)
Map<String, Integer> scores = Map.of("alice", 100, "bob", 200);
serializer.serializeMap(scores, String.class, Integer.class, wb);
```

## JsonPrimitiveType

jing-marshall-json provides a sealed interface `JsonPrimitiveType` for representing raw JSON values as field types in marshallable entities.

The primary use case is **mixed-type collections**. Since jing-marshall resolves element types at compile time (e.g., `List<Integer>` means every element is deserialized as `Integer`), there is no way to have a heterogeneous collection where elements are of different types. `JsonPrimitiveType` solves this — by declaring a field as `List<JsonPrimitiveType>`, each element can be a different JSON primitive type (bool, number, or string), and the actual type is determined at runtime from the JSON content.

Additionally, `JsonPrimitiveType` serves as a **bridge between primitive types and custom types**. When you register a custom type transformer, the "builtin" type in the transformer must be a `JsonPrimitiveType` subtype. The transformer converts between your custom type and a `JsonPrimitiveType`, which is then serialized to/deserialized from the corresponding JSON representation.

```java
public sealed interface JsonPrimitiveType
    permits JsonBoolType, JsonNumberType, JsonStrType {}

public value record JsonBoolType(boolean data) implements JsonPrimitiveType {}
public value record JsonNumberType(byte[] data) implements JsonPrimitiveType {}
public value record JsonStrType(String data) implements JsonPrimitiveType {}
```

Usage in a marshallable class:

```java
@Marshallable
public class DynamicPayload {
    private String type;
    private List<JsonPrimitiveType> values;
    private Map<String, JsonPrimitiveType> metadata;
}
```

During serialization, `JsonPrimitiveType` instances are written directly as their JSON representation:
- `JsonBoolType(true)` -> `true`
- `JsonNumberType("42".getBytes())` -> `42`
- `JsonStrType("hello")` -> `"hello"`

## Options

### Serializer Options

Built via `JsonSerializerOption.builder()`:

| Option | Default | Description |
|--------|---------|-------------|
| `serializeNullInObjOrMap` | `false` | Whether to include null values in objects/maps. When `false`, null fields are omitted entirely. |
| `indentationLevel` | `NONE` | `NONE` (compact), `TWO` (2-space indent), or `FOUR` (4-space indent). |
| `maxNestedSize` | `64` | Maximum nesting depth for objects, arrays, and maps. |
| `setTransformerClasses(Class<?>...)` | — | Register custom type transformers for converting non-standard types to/from `JsonPrimitiveType`. |

### Deserializer Options

Built via `JsonDeserializerOption.builder()`:

| Option | Default | Description |
|--------|---------|-------------|
| `ensureAllFieldsPresent` | `false` | If `true`, throws an exception when a JSON object is missing a field declared in the Java class. |
| `maxEmptyBytes` | `256` | Maximum bytes of whitespace to skip between tokens. |
| `maxNumberBytes` | `24` | Maximum bytes for a number literal. |
| `maxStringBytes` | `65535` | Maximum bytes for a string value. |
| `maxArrayElements` | `1000` | Maximum number of elements in an array. |
| `maxMapElements` | `200` | Maximum number of entries in a map. |
| `maxDummyElements` | `4` | Maximum unknown/ignored fields before throwing. |
| `maxNestedSize` | `64` | Maximum nesting depth. |
| `setTransformerClasses(Class<?>...)` | — | Register custom type transformers. The transformer's builtin type must be a `JsonPrimitiveType` subtype. |

## Custom Type Transformers

If your entity contains types that are not natively supported by the JSON engine, you can provide a `MarshallTransformer` implementation annotated with `@Transformable`. The `MarshallTransformerProcessor` will automatically generate a `MarshallTransformerFacade` for you.

The transformer's builtin type **must** be a `JsonPrimitiveType` subtype (`JsonBoolType`, `JsonNumberType`, or `JsonStrType`) when used with jing-marshall-json:

```java
@Transformable
public final class LocalDateTimeTransformer implements MarshallTransformer<LocalDateTime, JsonStrType> {
    private static final DateTimeFormatter formatter =
        DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");

    @Override
    public JsonStrType toBuiltin(LocalDateTime ct) {
        return new JsonStrType(formatter.format(ct));
    }

    @Override
    public LocalDateTime toCustom(JsonStrType bt) {
        return formatter.parse(bt.data(), LocalDateTime::from);
    }
}
```

The processor generates a `LocalDateTimeTransformerFacade` class automatically. Then configure the serializer/deserializer with the generated facade:

```java
JsonSerializerOption option = JsonSerializerOption.builder()
    .setTransformerClasses(LocalDateTimeTransformerFacade.class)
    .build();
```

Note: custom type transformers cannot override JDK built-in types (e.g., `int`, `String`) or marshallable bean types. The transformer's builtin type must be a `JsonPrimitiveType` subtype.

## Enum Serialization

Enums are serialized using their `mappedName` if configured via `@MarshallAttr`, otherwise using the enum constant's `name()`:

```java
@Marshallable
public enum Color {
    RED,
    GREEN,
    @MarshallAttr(mappedName = "\"BLUE_COLOR\"")
    BLUE
}
```

Serializes as: `"RED"`, `"GREEN"`, `"\"BLUE_COLOR\""`.

## Type Resolution Priority

When the serializer or deserializer encounters a field type, it resolves it in the following priority order:

1. **Natively mapped types** (highest priority) — types that have a direct, one-to-one mapping to a JSON representation: primitive wrappers (`Byte`, `Boolean`, `Short`, `Character`, `Integer`, `Long`, `Float`, `Double`), `String`, `CharSequence`, `JsonPrimitiveType` and its subtypes (`JsonBoolType`, `JsonNumberType`, `JsonStrType`), and primitive arrays (`byte[]`, `boolean[]`, `short[]`, `char[]`, `int[]`, `long[]`, `float[]`, `double[]`). These are serialized/deserialized directly by the engine without going through jing-marshall metadata.
2. **Custom types** — types registered via `setTransformerClasses`. The transformer converts the custom type to/from a `JsonPrimitiveType` for serialization/deserialization.
3. **Enums** — handled as a special case, using `MarshallFacade` mapped names.
4. **Marshallable beans** (lowest priority) — any other type is assumed to be a `@Marshallable` type, and the engine attempts to look up its `MarshallFacade` via `Marshalls.beanMarshallFacade()`. If the type is not marshallable (no facade exists), serialization/deserialization will fail.

Note: types like `UUID`, `BigInteger`, `BigDecimal`, date/time types, collections, and maps are **not** natively mapped by the JSON engine. If you need to serialize/deserialize these types as JSON primitives (e.g., `UUID` as a string, `LocalDateTime` as a formatted string), you must provide your own custom `MarshallTransformerFacade` implementation and register it via `setTransformerClasses`. The framework does not ship any built-in transformer implementations for these types. If a field type falls through all four levels above without a match, the engine cannot handle it and will throw an exception at runtime.

## Performance

### Overview

The vast majority of JSON processing overhead comes from string handling. There exist libraries that use `Unsafe` to directly access JDK's internal `String` representation, bypassing bounds checks and char-to-byte conversion — these can achieve several times the throughput of jing-marshall-json and are outside the scope of our comparison. Our benchmarks compare against **Jackson**, the most widely used JSON library in the Java ecosystem.

Compared to Jackson-like reflection-based JSON frameworks, the most significant advantage of jing-marshall-json is its **statelessness**. `JsonSerializer` and `JsonDeserializer` are extremely lightweight objects. Every intermediate object created during a single serialization or deserialization operation is transient — computed on the fly and discarded immediately, never pooled or reused. The entire system shares only one copy of the marshall metadata (`MarshallFacade`). This makes the system's complexity extremely low: no object pools, no cached state, no thread-local buffers, no configuration registries that need to be kept in sync. The serializer and deserializer hold only an immutable options object, and all runtime state is confined to the duration of a single operation.

Other performance advantages include:

- **Simpler internal paths** — no reflection, no generic type resolution at runtime, direct field access via generated code.
- **Vector API acceleration** — string serialization and deserialization use SIMD to batch-process characters for ASCII detection and escape scanning.
- **Zero-allocation number parsing** — all numeric paths parse byte-by-byte without intermediate object allocation. Integer and long use a LUT-based two-digit-at-a-time algorithm. Float and double use the uScale algorithm ([https://research.swtch.com/fp](https://research.swtch.com/fp)) for shortest-path representation — the minimal string form that guarantees exact roundtrip of the binary representation.

If Jackson were to adopt a similar approach (generated accessors + Vector API), it would likely achieve comparable performance numbers. Performance should not be the primary reason to choose jing-marshall-json — its core advantage is **simplicity and statelessness**.

### Benchmarks

Benchmarks were run on an **AMD Ryzen 9 7900X** CPU, using the **twitter.json** dataset (632 KB) — a widely-used open dataset representative of real-world API responses.

### Floating-Point Number Format

Floating-point numbers are formatted following the same rules as JDK:

- In the range 10^-3 to 10^7 (exclusive), direct decimal notation is used (e.g., `3.14`, `0.001`, `1000000.0`).
- Outside this range, scientific notation is used (e.g., `1.5E10`, `1.23E-100`).

One difference from JDK: jing-marshall-json uses **shortest-path representation** via the uScale algorithm. This means a floating-point number is mapped to its shortest string form that roundtrips to the exact same binary representation. JDK enforces at least one digit after the decimal point (e.g., `4.9E-324` for `Double.MIN_VALUE`), whereas jing-marshall-json may output `5E-324` — a shorter form that corresponds to the same IEEE 754 bit pattern.

For scenarios involving heavy JSON floating-point parsing, jing-marshall-json is particularly well-suited. Its float/double parsing performance is approximately **2~3x faster** than JDK's `Float.parseFloat()` / `Double.parseDouble()`. The primary reason is its simpler algorithm — the uScale-based parser is significantly more straightforward than JDK's general-purpose parsing logic. A secondary benefit is that it parses directly from the byte buffer without intermediate `String` allocation.

## Constraints

- Map keys must be `String` or `CharSequence`.
- Primitive arrays (e.g., `int[]`, `double[]`) are supported directly; wrapper arrays (e.g., `Integer[]`) are supported through the marshalling system.
- Multi-dimensional arrays are not supported, as they are not part of jing-marshall's type system.
- Generic bean types (e.g., `Result<T>`) are not supported due to generic erasure in jing-marshall.
- Nested generic containers (e.g., `Map<List<X>, Y>`) and generic fields with more than 2 type parameters are not supported, as jing-marshall only captures at most 2 generic type arguments at the first level.
- Recursive structures (e.g., a tree node with left/right children of the same type) are fully supported.
